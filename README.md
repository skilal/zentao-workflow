# 禅道需求开发工作流 · 网页版

在浏览器中选择指派给当前账号的需求、任务或 Bug，自动确定前后端项目分支。每轮计划未提问且一次完整生成时自动实施；有提问或多回合补充时等待确认。可选在实施后先做编译检查，再按固定提示词 Review，无遗留问题时自动本地 commit，全程不 push。

网页只展示和控制流程；禅道访问、Codex 会话及 Git 操作均由本机 Python 服务完成。服务固定监听 `127.0.0.1`，不发布到外部站点。

## 启动与停止

使用 Windows、Python 3.11 或以上、Git，以及已登录的 Codex CLI。运行时只使用 Python 标准库和已随项目保存的前端资源，不需要 Tkinter、Node、npm 或联网加载页面组件。

首次下载并配置：

```powershell
git clone https://github.com/skilal/zentao-workflow.git zentao-codex-workflow
Set-Location -LiteralPath '.\zentao-codex-workflow'
Copy-Item -LiteralPath '.\settings.example.json' -Destination '.\settings.json'
```

在 `settings.json` 中填写禅道地址、账号及实际仓库路径，并确认 `codex.command` 对应本机可用的 Codex CLI。示例使用 Windows 的 `["codex.cmd"]`，`app-server --listen stdio://` 由程序统一追加，不要写入配置。密码在启动后的“工作流设置”中保存。已有本地配置时直接使用，不要再次复制模板覆盖。

若提示“找不到配置中的 Codex 命令”，在能使用 Codex 的 PowerShell 中执行 `(Get-Command codex).Source`，将实际可执行文件的绝对路径填入 `codex.command` 的第一个元素，例如 `["C:/实际安装目录/codex.exe"]`，保存后重启本地服务。网页设置不提供命令路径编辑。短命令名只从服务进程继承的 `PATH` 查找，可能与终端环境不同；安装位置改变后需更新该路径。

启动已有项目：

```powershell
Set-Location -LiteralPath 'D:\wkproj\zentao-codex-workflow'
.\launch.ps1
```

脚本启动本地服务并打开浏览器，默认地址为 **http://127.0.0.1:8765/**。需要只启动服务时运行 `py -3 -X utf8 app.py --no-browser`。端口在 `settings.json` 的 `web.port` 中明确配置，占用时会停止，不自动更换端口。

关闭网页不会终止已确认的后台任务；需要停止时，在“工作流设置”点击“暂停并停止本地服务”，或在启动终端按 Ctrl+C。会话会保存，服务重新启动后恢复查看，业务执行不会自动继续。

## 使用流程

1. **工作项与资料**：启动后尝试连接禅道一次，不自动重试登录。列表按类型和编号区分，支持筛选和搜索；勾选后自动读取正文、图片、附件及关联需求。任务支持多选，同一项目下的前后端任务可合并到一次计划与开发会话；需求和 Bug 保持单选。相同内容及版本的关联需求、共享附件自动去重，不同版本或正文分别保留；图片和附件显示在对应的任务或需求描述下，历史会话也按原始资料恢复归属，并保留全部选中任务。
2. **补充需求**：在工作项页面填写必要业务规则、验收标准或附件关键内容，可多选、分批上传图片，也可在补充输入框中粘贴截图。支持 PNG、JPEG、GIF、WebP、BMP，单张大小沿用 `zentao.max_attachment_mb` 配置。图片保存在当前会话中，可预览、移除，刷新页面或重启服务后保留，并随需求送入分析；上传失败时须明确重试或移除，再点击“开始需求分析与计划”。开始计划后图片只读。所有工作项都固定准备 `frontend`（ais-web）和 `backend`（ais-server）两个仓库。
3. **自动确定分支**：优先复用项目常用分支；未配置时由 AI 结合所属项目、工作项内容与分支元数据判断。无法明确时才等待人工选择。确定后优先复用已检出目标分支的目录，其次在空闲目录切换分支，没有空闲目录才创建 worktree。原有未提交修改由 Git 保留，不自动修改或纳入任务提交；切换冲突时停止，不暂存、丢弃或自动提交这些改动。
4. **计划与会话**：原生问题逐项等待回答，没有预选答案或超时放行。每轮计划独立判断，未提问且首个回合完整生成有效计划时自动授权实施；有提问或多回合补充时，明确点击“确认当前计划并实施”。回答问题、补充缺失资料、暂停恢复不会清除本轮记录；明确调整已生成计划或实施中重新计划时开启新一轮。历史会话缺少记录时仍需人工确认。
5. **后端编译检查与会话内 Review**：开启编译检查后，每轮实施或修复先按模块检查有任务改动的后端，缺依赖时等待人工选择。前端不执行构建或准备依赖，继续参与 Review。检查通过或明确跳过后自动审查，校验完整 JSON 或 JSON 代码块后，在原会话消息中显示可勾选问题卡片，无需切换页面。问题区分本次引入、原有问题和证据不足，展开查看依据、建议及业务影响。仅最新轮次可操作，历史轮次只读，可展开查看输出原文。只修复选中项；默认最多三轮修复复审，加上首次 Review，最多四次审查。
6. **本地提交**：首次 Review 或修复复审合并旧问题后，无遗留问题时自动 commit 到已确定的本地项目分支；仍有问题时，须选中全部剩余问题并填写接受原因。达到轮次上限仍有问题时暂停，可明确追加一轮。提交失败后停止，可点击“继续本地提交”；部分成功时只继续未完成仓库，不自动重试。

“查看累计代码差异”包含已有文件差异和新增文本文件内容。每个仓库分别记录 commit；部分提交失败会保留已成功的结果，不自动回滚或重复提交。不 push、不修改禅道状态。

### 已完成会话的后续对话与可选 Review

需求开发完成后，可在原“计划与会话”页面继续提问、获取信息或提出修改要求，并上传或粘贴图片。至少填写文字或上传一张图片，点击“发送”后沿用原 Codex 线程和需求上下文。获取信息时只读取并回答，明确要求修改时才处理对应范围；关键规则不清时仍等待回答，扩大范围时仍先重新计划。原线程无法恢复时停止，不自动新建线程替代。

续聊输入区提供“修改后自动 Review”开关，每条新消息默认关闭。关闭时，回答或修改完成即结束本轮，不自动审查、不自动提交，修改保留在工作区；开启且本轮有受控代码修改时，使用固定 Review 提示词审查，后续问题选择、修复复审及本地提交沿用现有流程。纯问答无代码修改时，即使开启也跳过审查和提交。跳过审查的轮次显示“已完成（未审查）”，可以继续对话和上传图片。首次需求实施仍自动 Review 并按现有规则本地提交。

每条后续消息形成独立交付轮次，原消息、图片、计划、审查及提交记录保留，并记录本轮 Review 开关。开关随当前文字草稿按浏览器标签页保存，发送成功后下一条重置为关闭，发送失败保留选择。已发送轮次的开关随会话持久化，暂停、恢复及重新计划不改变。历史运行中轮次缺少开关字段时维持原有流程。图片在发送前可移除，发送后在对应消息中只读展示；上传失败须明确重试或移除后再发送。待发送的已上传图片和正式消息可在刷新或重启后恢复。历史 Review 只读，本轮只合并本轮审查问题，不把上一轮已接受问题自动列为待修复。

后续对话固定沿用原前后端仓库与目标分支，重新按现有目录分配规则确定工作区，并以目标分支当前 HEAD 建立本轮基线。目录切换冲突、原分支被占用或 Git 钩子阻止操作时明确停止，人工处理后点击“从暂停点继续”，不会重复创建消息。已有本机改动及上轮未提交代码仍保留且不自动修改或纳入本轮提交；需要修改同一文件时等待明确指示。本轮首次修改不占用 Review 后的问题修复次数，复审次数沿用配置；后续提交使用 `fix(...)`，部分成功时仅继续未完成仓库。完成后可再次发送消息，不 push、不修改禅道状态。

本地接口 `/api/actions` 新增 `followup`，以 `data.text`、`data.image_ids` 和必填布尔值 `data.review_enabled` 提交本轮消息，沿用 `session_id`、`revision` 和 `request_id`。图片接口以 `purpose=followup` 管理后续对话图片，省略用途仍按原需求补充图片处理。删除会话纳入历次自建工作区，继续检查其他会话占用与未提交文件，保留复用目录。

### 所属项目与分支识别

工作项列表和资料快照保留所属项目编号、名称及多个项目候选。任务详情仅返回编号时，通过项目详情接口补齐名称。归属缺失或多个项目时，先明确本次所属项目，不用产品或迭代名称代替。前后端分支分别判断，名称可以不同。

AI 读取工作项正文、补充说明、真实分支名称、最新提交时间和提交说明，以结构化结果返回选择依据或待回答问题。该阶段不提供业务文件工具，不设置 `develop`、`master`、`feature` 等名称的固定优先顺序，也不把时间最新当作正确依据。

没有合适分支，或目标仅存在于缓存远程引用时，对对应仓库执行一次 `git fetch origin --no-tags`（远程名称由配置明确指定），再核对远程实际存在的分支并重新判断。鉴权或网络失败即停止；恢复操作不会切换凭据、远程或模型。已被远程删除的缓存引用不会当作有效远程分支使用。

AI 无法确定时，页面展示依据、候选和疑问，必须明确选择后才能继续。“保存为项目常用分支并继续”按禅道站点、项目编号和仓库角色保存人工选择；AI 自动结果只用于当前会话。后续优先复用常用分支，失效时要求重新选择。在创建工作区之前，可通过“更换项目常用分支”主动调整。

现有本地分支直接使用当前提交，不自动合并或重置。仅有远程分支时，刷新后创建同名本地跟踪分支，在分配的目录中修改、提交。空闲目录限配置的原仓库及已完成会话管理的目录；其他工具创建的工作区不自动接管。暂停、失败或待确认的会话仍保留目录占用，完成或删除后释放。不会自动创建另一条工作项分支。已有工作区的历史会话继续使用原分支，不根据历史记录生成项目常用分支。

复用目录开始时已有的已暂存、未暂存和未跟踪改动按文件登记为本机保留内容，不进入任务差异、审查清单和提交；已有暂存状态也会保留。文件工具拒绝自动修改这些文件，需要改动时须先取得用户明确指示。任务提交只包含本次任务的文件。分支切换仍受 Git 自身的覆盖检查约束，冲突即停止，不自动切换其他方案。

### 任务关联需求资料

普通任务（`fromBug` 为 0）的关联需求固定使用任务详情接口返回的 `storySpec`、`storyVerify`、`storyFiles`，保留关联编号、标题和 `storyVersion`，不再单独请求需求详情。这样可兼容当前禅道中关联需求实际类型为 `requirement`、按研发需求接口读取却报“对象不存在”的情况。

普通任务的页面会标注“来自任务详情的关联需求资料”和关联版本；内容对应任务所关联的版本，可能不是需求的最新版本。该关联资料不会作为独立用户需求加入待办列表。正文图片、附件及飞书链接仍按现有规则处理。

来源 Bug 的任务（`fromBug` 非 0）由禅道返回来源 Bug 描述，不包含上述关联需求正文字段。因此这类任务保留原有读取路径：有需求关联时请求需求详情，再读取来源 Bug 详情，正文、验收标准、图片和附件一并采集。不将需求接口返回的资料标为任务内嵌资料或任务所关联版本；关联请求失败时明确停止，不自动重试或尝试其他需求类型。

关联正文为空而任务描述有效时，可依据任务内容进入计划，不会将任务描述复制成需求正文。任务和关联资料均无有效正文时仍要求补充；描述冲突或验收标准不清时在计划阶段询问。附件缺失继续提示人工补充，任务自身读取失败或权限失效仍停止，不自动重试。独立需求、Bug 及任务来源 Bug 的读取规则不变。

## 刷新与历史

- 实施计划和 Codex 消息支持 Markdown 标题、列表、任务列表、表格、引用、链接和代码块，兼容 `<proposed_plan>` 包裹；渲染使用本地资源并清理 HTML，原始计划及确认版本不变。Review 的选择、复审、追加轮次、接受原因及本地提交记录统一在“计划与会话”中查看。

- 会话卡片顶部显示独立的会话标题，初始沿用任务类型、编号和标题的现有命名方式；点击“改名”可自定义，刷新或重启后保留。下方始终显示原任务、需求信息，搜索同时匹配自定义标题与工作项信息。

- 会话按禅道项目分区展示，可添加当前账号可见的项目；未启动的会话可拖动或通过“移动”更换项目。项目分区按站点保存在本地，不在禅道创建项目。
- 添加项目分区和确认项目归属使用可搜索的项目下拉框，支持按名称或编号匹配；选中后自动使用禅道项目名称。目标分支下拉框支持按显示名称搜索。

- 工作项、计划和 Review 页面左侧统一显示会话列表，支持新建、标题或编号搜索、状态筛选、切换与删除。原“历史会话”入口并入这里。
- 支持多个会话同时运行；每个会话有独立的执行队列、Codex 连接、输出与操作版本。切换只改变查看对象，不会暂停或重启其他会话，后台问题会标记在对应会话上。
- 同一个目录同一时间只供一个未完成会话使用。目标分支目录由其他未完成会话占用时提示路径及会话，不重复检出同一分支或自动另建分支；其他空闲目录可切换到未检出的目标分支。目录分配、占用登记及 Git 共享元数据操作按仓库串行处理。
- 新建会话后勾选工作项自动读取资料，任务可多选联合开发；开始计划前更改选择更新同一个草稿会话，开始计划后工作项固定。
- 浏览器刷新后重新加载当前工作项、阶段、计划、待回答问题、Review 和提交记录。当前选择按浏览器标签页保存，不同标签页可分别查看不同会话。
- 已输入但未提交的补充说明、工作项选择、问题答案、人工分支选择和 Review 选择按会话分别保存为当前标签页草稿。密码不进入草稿。
- 实时输出通过 SSE 推送，连接中断后恢复事件流；服务重启后需刷新页面重新连接。
- 服务重启后所有中断执行的会话显示为已暂停，须人工继续；资料读取中断时显示读取失败，可重新勾选读取。停止服务会保存并关闭全部会话。
- 删除会话时一并删除本地资料、附件和本会话新建的独立工作区，保留复用目录、Git 分支及提交。执行中的会话须先暂停并等待结束；待删除工作区存在未提交、未跟踪文件或被其他未完成会话使用时会阻止删除。复用目录中的本机保留改动不影响仅删除会话记录。
- 工作区全部预检通过后逐个移除，不使用强制删除。中途失败保留会话记录及清理进度，再次删除只处理剩余工作区；清理过部分工作区的会话只能继续删除。
- 原桌面客户端的 JSON 会话、附件及 Windows 加密凭据继续使用，不要求重新配置账号。

## 配置与凭据

### Review 前的可选后端编译检查

在“工作流设置”勾选“Review 前自动检查后端编译”可设置新会话默认值；开始会话前可单独调整，开始后固定并沿用到后续对话。配置字段仍为 `compile_check.enabled`，初始为 `false`，已有开关值保留。开启后，每轮实施或修复完成，只检查有任务改动的后端，再按原 Review 设置继续；仅有前端改动时直接进入原有 Review 流程。后续对话关闭 Review 时，后端编译检查完成后仍只保留修改，不自动审查或提交。

后端复用 Maven 本地仓库，先离线执行 `compile`，按改动所属模块及所需模块检查。例如修改档案服务即检查档案服务及其所需模块；工程级配置变化检查整个工程。不执行测试、打包、`install` 或发布。工具或配置不兼容时停止，不自动更换版本或切换依赖源。前端不再调用 pnpm、不安装依赖，也不受前端锁文件与工具版本影响；前端代码仍完整参与 Review。已有相关 Git 钩子时仍停止，不禁用或绕过。

缓存不足时，必须明确点击“允许下载并继续”“跳过该仓库本轮检查”或“暂停”，无默认答案。下载和跳过只对当前仓库、本轮代码与依赖配置有效，后续新检查不会继承授权；下载失败后停止。页面只展示状态、必要摘要及脱敏代码诊断，不展示原始编译日志。

诊断明确位于本轮修改代码时自动修复并重查；原有、环境、网络及原因不明的问题暂停。自动修复沿用会话修复上限，每次进入 Review 前独立计数，不占 Review 修复次数，超限可人工追加一轮。通过或被明确跳过后才进入 Review，检查结果随 Review 上下文提供。暂停或停止服务会终止检查进程，重启后须人工恢复；普通恢复不会代替下载、跳过等选择。

提供给模型的检查上下文仅包含当前交付的状态、模块、必要诊断及受控修复范围，不传文件哈希、人工授权明细或时间戳。Review 与修复提示词不再重复附带检查记录；完整记录仍保存在本机会话中。旧的前端检查历史保留，尚在等待的前端检查可点击“前端检查已取消，继续后端流程”继续，不执行前端命令。

本地接口 `/api/actions` 增加 `compile_decision`，`data` 包含 `batch_id`、`repository`、`decision`；操作为 `download`、`retry`、`skip`、`pause`、`add_round`，沿用会话版本和请求去重。`plan` 与设置保存使用 `compile_check_enabled` 布尔值。

`settings.json` 是唯一的本地运行配置文件，保存禅道地址、账号、仓库路径、项目常用分支、Codex 命令、默认模型、推理强度和修复轮次，已加入 Git 忽略规则。公开仓库只维护脱敏模板 `settings.example.json`。

网页“工作流设置”支持从本机 Codex 的可用模型中选择默认模型与推理强度。模型选择“沿用本机 Codex”时，`codex.model` 保持为空；`codex.reasoning_effort` 保存明确的强度。模型和强度以本机返回的列表为准，点击“刷新模型列表”可重新读取；无法读取或组合无效时不会启动会话或自动更换模型。

在工作项资料下方、点击“开始需求分析与计划”前，可以单独调整本次会话的模型与推理强度，不改变全局默认值。开始时将实际模型及强度保存到会话，之后识别分支、计划、实施、Review 和暂停恢复均使用该配置；刷新页面或重启服务后仍保持。切换模型后若原强度不受支持，需重新选择。旧会话未保存模型配置时，继续前需先在“计划与会话”页面选择并保存一次。

`repositories` 必须恰好登记一个 `role: "frontend"` 和一个 `role: "backend"`，每项明确填写 `name`、`path`、`remote`。`project_branches` 初始为 `{}`，页面确认后按“站点 → 项目编号 → branches → frontend/backend”保存常用分支；不会从项目名称猜测仓库角色。升级旧配置时，为已有两端仓库补齐角色与远程字段，保留原账号、路径及其他设置。

`prompts/review.md` 保存用户提供的固定 Review 原文。流程开始后锁定配置；流程内若提示词被外部改写，会明确停止。

密码仅通过 Windows 当前用户 DPAPI 加密保存在 `.local/zentao-password.bin`。页面不回显密码，服务不向前端返回禅道 Token。`.local/` 和 `work/` 已加入忽略列表，包含业务资料或检查中间文件，不应上传或提交。

## 后续开发与推送

直接在当前目录开发、提交和推送，无需同步到其他副本。本地 `settings.json`、加密凭据及会话资料继续使用，Git 更新不覆盖它们。修改配置结构时同步更新 `settings.example.json`，使用者再按模板手动调整本地配置。

```powershell
git diff
git add README.md
git commit -m "docs(workflow): 完善工作流使用说明"
git push origin main
```

上面的 `git add` 路径按本次实际修改文件替换。提交采用 `type(scope): 中文说明`，详细约定见 [贡献与提交规范](CONTRIBUTING.md)。应用自身只进行本地提交；向 GitHub 推送由使用者明确操作。

## 页面与本地接口

前端使用 AIS 项目已有的 React、Ant Design 和 dayjs 发布资源，采用相同的主题色、按钮、表格、表单及弹窗组件体系。资源已复制到 `web/dist/vendor/`，版本记录和许可证一并保留，页面不访问外部 CDN，不需要构建。

本地 HTTP 服务提供工作流操作、分支读取、差异查看、受限附件访问及 SSE。`GET /api/session?id=...` 读取指定会话，差异接口使用 `session_id` 指定会话；`/api/actions` 按 `session_id` 分发操作，包含 `delete_session` 删除操作。会话 SSE 携带 `session_id`，完整状态还包含版本和事件游标。操作要求本机来源、会话 Cookie、独立操作凭据及明确请求标识；重复请求不会重复执行。计划确认、修复选择、提交和删除还检查页面所见的会话版本。

核心仍由 `workflow/engine.py`、`rpc.py`、`mcp_server.py`、`gitops.py` 等模块负责。原生只读沙箱与受控 MCP 文件工具继续使用；文件写入只在已确认的实施、修复阶段授权。

## 支持范围

- 禅道 API v1：账号密码登录、当前用户、分页待办、详情、关联需求 / 来源 Bug、附件及正文图片。
- 文本提取：UTF-8 文本及不含内嵌媒体的 DOCX、PPTX。PDF、电子表格、扫描件、旧版 Office、压缩包、加密文档及含内嵌媒体的文件明确提示人工补充。
- 飞书第一版不读取，只保留链接；必要规则由人工补充。
- “需求”对应研发需求 story，另有任务 task、Bug bug；不混入用户需求 requirement 或业务需求 epic。
- 模型对 Java 代码只做轻量静态检查；开启编译检查时仅由控制器执行受控例外。工作流自身的模拟验证不编译业务仓库、不下载业务依赖，业务功能仍需人工验收。

Codex 官方协议参考：[App Server](https://learn.chatgpt.com/docs/app-server)、[功能配置](https://learn.chatgpt.com/docs/config-file/config-basic)。
