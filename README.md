# 禅道需求开发工作流 · 网页版

在浏览器中选择指派给当前账号的需求、任务或 Bug，自动确定前后端项目分支。每轮计划未提问且一次完整生成时自动实施；有提问或多回合补充时等待确认。可选在实施后先做编译检查，再按固定提示词 Review，无遗留问题时自动本地 commit，全程不 push。

网页只展示和控制流程；禅道访问、Codex 会话及 Git 操作均由本机 Python 服务完成。服务固定监听 `127.0.0.1`，不发布到外部站点。

## 启动与停止

使用 Windows、Python 3.11 或以上、Git，以及已登录的 Codex CLI。运行时只使用 Python 标准库和已随项目保存的前端资源，不需要 Tkinter、Node、npm 或联网加载页面组件。

首次下载并配置：

```powershell
git clone https://github.com/skilal/zentao-workflow.git zentao-codex-workflow
Set-Location -LiteralPath '.\zentao-codex-workflow'
Copy-Item -LiteralPath '.\settings.example.json' -Destination '.\settings.json'
```

在 `settings.json` 中填写禅道地址、账号及实际仓库路径，并确认 `codex.command` 对应本机可用的 Codex CLI。示例使用 Windows 的 `["codex.cmd"]`，`app-server --listen stdio://` 由程序统一追加，不要写入配置。密码在启动后的“工作流设置”中保存。已有本地配置时直接使用，不要再次复制模板覆盖。

若提示“找不到配置中的 Codex 命令”，在能使用 Codex 的 PowerShell 中执行 `(Get-Command codex).Source`，将实际可执行文件的绝对路径填入 `codex.command` 的第一个元素，例如 `["C:/实际安装目录/codex.exe"]`，保存后重启本地服务。网页设置不提供命令路径编辑。短命令名只从服务进程继承的 `PATH` 查找，可能与终端环境不同；安装位置改变后需更新该路径。

启动已有项目：

```powershell
Set-Location -LiteralPath 'D:\wkproj\zentao-codex-workflow'
.\launch.ps1
```

脚本启动本地服务并打开浏览器，默认地址为 **http://127.0.0.1:8765/**。需要只启动服务时运行 `py -3 -X utf8 app.py --no-browser`。端口在 `settings.json` 的 `web.port` 中明确配置，占用时会停止，不自动更换端口。

关闭网页不会终止已确认的后台任务；需要停止时，在“工作流设置”点击“暂停并停止本地服务”，或在启动终端按 Ctrl+C。会话会保存，服务重新启动后恢复查看，业务执行不会自动继续。

## 内置提示词

左侧“内置提示词”菜单独立展示各阶段的组装模板、组成原文、生效条件及来源，默认打开“需求分析与计划”。窄屏使用横向阶段导航，支持切换模板变体、展开片段和复制全文。通用规则单独展示；资料读取、工作区准备、实际编译和本地提交标明控制器职责。

本页只读，不读取具体会话或业务仓库资料，不调用模型或启动工作流。模板中的占位符表示需求、仓库、诊断、人工回答及历史审查等动态数据；图片引用、输出 Schema 和工具定义不展开为提示词正文。展示原文与执行端共用来源，进入页面或点击“刷新”读取当前内容，读取失败仅在人工重试后重新请求。

原“工作流设置”中的固定 Review 提示词编辑入口保留。提示词页面展示当前文件内容，已有会话可能继续使用保存的审查快照。只读接口 `GET /api/prompts` 沿用本机访问和页面 Cookie 校验，不接受查询参数或写入请求，不要求连接禅道或选择会话。

## 使用流程

模型回合结束后，控制器核对代码差异和修改归属时显示“核对改动中”。重复内容的版本比较会复用结果，重复片段的编号集中统计；片段编号及归属规则保持一致。核对期间可暂停，暂停后不会继续启动检查或审查。

1. **工作项与资料**：启动后尝试连接禅道一次，不自动重试登录。列表按类型和编号区分，支持筛选和搜索；勾选后自动读取正文、图片、附件及关联需求。任务支持多选，同一项目下的前后端任务可合并到一次计划与开发会话；需求和 Bug 保持单选。相同内容及版本的关联需求、共享附件自动去重，不同版本或正文分别保留；图片和附件显示在对应的任务或需求描述下，历史会话也按原始资料恢复归属，并保留全部选中任务。
2. **补充需求并开始计划**：在工作项页面填写必要业务规则、验收标准或附件关键内容，可多选、分批上传图片，也可在补充输入框中粘贴截图。支持 PNG、JPEG、GIF、WebP、BMP，单张大小沿用 `zentao.max_attachment_mb` 配置。查看资料和上传图片仅属于当前页面的临时查看，不创建会话；刷新、关闭页面或放弃查看后不恢复这些内容。上传失败时须明确重试或移除，再点击“开始需求分析与计划”。服务端接受开始计划后才正式创建会话，将资料、补充说明及图片保存到会话中，刷新或重启后可恢复，并随需求送入分析；开始计划后图片只读。所有工作项默认准备配置中的 `frontend`（ais-web）和 `backend`（ais-server）两个仓库；已有会话可按下述人工确认流程更换本会话目录。
3. **自动确定分支和目录**：优先复用项目常用分支；未配置时先提取项目地名或主体关键词，本地筛选命中分支并读取提交记录，让 AI 直接选择一条对应项目最新的开发主线，排除功能、临时修复及备份分支。前后端独立优先复用检出目标分支的目录，多个匹配采用 HEAD 提交者时间最新者；无匹配则切换空闲候选目录，没有空闲目录便在 D 盘创建工作区。时间并列或检测失败仍等待人工选择。本机已有修改保留且排除。
4. **计划与会话**：模型通过 `workflow.ask_user` 将问题交给控制器，控制器保存问题并结束当前模型回合，在现有问题卡片中逐项等待回答，不在模型回合中 sleep 或轮询。没有预选答案或超时放行，重启后待答问题仍保留。每轮计划独立判断，未提问且首个回合完整生成有效计划时自动授权实施；有提问或多回合补充时，明确点击“确认当前计划并实施”。回答问题、补充缺失资料、暂停恢复不会清除本轮记录；明确调整已生成计划或实施中重新计划时开启新一轮。历史会话缺少记录时仍需人工确认。
5. **后端编译检查与会话内 Review**：开启编译检查后，每轮实施或修复先按模块检查有任务改动的后端，缺依赖时等待人工选择。前端不执行构建或准备依赖，继续参与 Review。检查通过或明确跳过后自动审查，校验完整 JSON 或 JSON 代码块后，在原会话消息中显示可勾选问题卡片，无需切换页面。问题区分本次引入、原有问题和证据不足，展开查看依据、建议及业务影响。仅最新轮次可操作，历史轮次只读，可展开查看输出原文。只修复选中项；默认最多三轮修复复审，加上首次 Review，最多四次审查。
6. **本地提交**：只勾选要修复的问题，点击修复后，未选项记为本轮不修复，保留记录但不再阻塞提交，无需填写原因。首次 Review 无问题，或选中项解决且无新待处理问题时，自动 commit 到已确定的本地项目分支；全部不修复时可直接点击“不修复剩余问题并本地提交”。复审新发现的问题仍等待人工选择。达到修复轮次上限可明确追加一轮，也可选择不修复剩余问题并提交。提交失败后停止，可点击“继续本地提交”；部分成功时只继续未完成仓库，不自动重试。

“查看累计代码差异”包含已有文件差异和新增文本文件内容。每个仓库分别记录 commit；部分提交失败会保留已成功的结果，不自动回滚或重复提交。不 push、不修改禅道状态。

工作区 HEAD 被人工提交、回退或更新，或在同一目录手工切换分支后，先暂停并等待当前操作结束，在“流程操作”点击“变更目录与审查基线”。弹窗中可保留现有目录，或分别填写新的前后端 Git 仓库绝对根目录，再点击“预览目录与基线”。目标目录须已检出分支，且未被其他未完成会话占用；明确确认后采用该目录当前分支与 HEAD 更新本会话目标分支及审查基线，同一目录只改变分支、HEAD 未变时也支持确认。不会自动切分支，更换目录时不接管会话自建工作区。原目录处于游离 HEAD 时，可直接填写已检出分支的新目录，无需先恢复原目录。部分提交和未答问题须先处理。

预览展示前后端旧、新目录、旧、新目标分支、旧基线、目标目录当前 HEAD 及本机保留文件。原目录不变时展示基线提交差异，保留原有本轮未提交差异及本机文件排除规则；更换目录时统一按新目录 HEAD 重新建立基线，不跨目录比较提交，旧目录未提交文件仅列出且留在原处，不自动搬迁。新目录已有的已暂存、未暂存和未跟踪文件全部登记为本机保留内容，不自动修改或纳入任务提交。只有明确点击“确认变更并保留会话”才会应用；预览后目标目录代码、暂存区、分支、HEAD 或占用关系再变动时必须重新预览确认。

确认前将完整会话备份到会话目录的 `baseline-backup-*.json`，保留原 Codex 线程、聊天、计划、附件、历史审查和修复选择，只更新当前会话的目录绑定、目标分支和基线，全局仓库配置、项目常用分支与禅道项目归属不变；不执行 reset、checkout 或修改代码、暂存区。后续续聊沿用新目录与新目标分支，旧目录记录仍保留，原自建工作区继续纳入占用与删除清理，复用目录不删除。新基线之前的已提交代码不再属于本轮累计差异，本机保留文件继续排除。旧审查与检查结论失效，审查阶段点击“从暂停点继续”会重新进入检查和 Review；计划、实施或续聊按原阶段继续，计划阶段仍须明确确认。此操作不会自动继续、自动提交或 push。

工作项资料包含任务、Bug、业务需求、用户需求及研发需求的正文和评论，评论保留作者、时间、所属动态及图片位置；编辑、完成、关闭等操作附带的非空备注也会读取。评论中的禅道图片与正文图片共用下载、预览及模型图片输入，相同文件只下载一次。支持带 `fileID` 的图片链接和 `file-read-编号.扩展名` 链接；站外、无法识别或无权限的图片会明确提示，不视为已读取。任务关联需求的正文沿用任务绑定版本，评论取当前需求动态。

列表继续显示指派给当前账号的待处理工作项；“按编号读取”可人工指定类型和编号，读取已完成、已关闭或已转交的工作项，无须重新激活或重新指派，访问权限由禅道接口校验。查看后仍在点击“开始需求分析与计划”时才创建正式会话。

已关联工作项的会话可点击顶部“工作项资料”，在右侧抽屉查看本会话保存的任务、关联需求、正文、评论、图片和附件。计划、实施、审查、暂停和完成阶段均可查看，后台任务继续执行；关闭后保留未发送草稿和会话阅读位置。抽屉默认展示资料快照，切换会话、新建会话或离开页面时自动关闭。在开始计划前、暂停后或已完成会话中，可点击“刷新正文与评论”重新读取禅道资料；待答问题须先处理，执行中不允许刷新。已完成会话刷新后，后续消息使用最新资料，原线程、工作区和审查基线保留；读取失败时保留原快照及其图片。

### 回答问题时上传附件

计划生成过程中，每个问题都可单独上传任意格式的文件，支持多选、分批上传及在该题输入框粘贴图片。每题填写文字、选择选项或上传附件之一即可作答；单个文件沿用配置中的附件大小上限。上传成功不会自动继续，所有问题作答完成且失败附件已重试或移除后，点击“提交回答并继续”。

已上传附件在刷新、重启后保留，提交后按题目显示在对话历史中。Codex 在原线程收到题目与附件的对应关系，图片随回合传入，其他文件可通过只读附件工具获取。任意文件均可保存，但内容读取只复用现有解析能力；不支持的格式会明确显示读取限制，不能把“已收到附件”当作“已读取内容”。

### 续聊上传 ZIP

续聊输入区支持“上传 ZIP”，可多选并与文字、图片一同发送，也可仅发送 ZIP。单个压缩包沿用 `zentao.max_attachment_mb` 上限（默认 20 MB）；上传中或失败未处理时不能发送，须明确重试或移除。上传本身不会发起对话。未发送附件可移除，发送后绑定对应历史消息，刷新、重启后保留，可下载原包并在后续对话继续引用。

续聊 ZIP 保留完整相对路径、中文文件名及显式空目录，只读取 XML 原文，保留标签和属性；按 BOM 或 XML 声明识别编码，无声明按 UTF-8 读取。OFD、PDF、图片、嵌套 ZIP 等其他文件仅显示路径、类型和大小，不解析或展开。包内最多 200 个文件，XML 解压总大小最多 16 MB、文本总量最多 25 万字符，其他格式不计入 XML 内容上限。无效或超限 ZIP 明确提示；单个 XML 损坏、加密或编码不支持时标记对应路径，其余可读内容仍可使用。AI 通过只读工具按成员编号分页读取 XML，不执行附件内容，不将其作为授权。首次需求补充、逐题回答及禅道附件的行为不变。

### 已完成会话的后续对话与可选 Review

每次需求实施或续聊产生的文件改动会在对应对话下展示为“本次改动”，按前端、后端列出，点击文件可查看本次差异。同一个文件在多次对话中被修改时，各自展示该次的差异。继续回答澄清问题或处理当前需求的修复仍归入同一次对话；纯问答没有改动卡片。文件记录随会话保存，刷新后仍可查看。升级前无法关联到对话的改动集中显示在“历史改动文件”。

全部修改结束后，会话仍展示一份“整体改动说明”，按业务页面合并位置和简短描述。Review 汇总实施及修复后的整体结果；关闭自动 Review 的续聊在修改结束时汇总，纯问答不更新。缺少整体改动说明不阻塞审查或提交。

需求开发完成后，可在原“计划与会话”页面继续提问、获取信息或提出修改要求，并上传或粘贴图片。至少填写文字或上传一张图片，点击“发送”后沿用原 Codex 线程和需求上下文。获取信息时只读取并回答，明确要求修改时才处理对应范围；关键规则不清时仍等待回答，扩大范围时仍先重新计划。原线程无法恢复时停止，不自动新建线程替代。

续聊输入区提供“修改后自动 Review”开关，每条新消息默认关闭。关闭时，回答或修改完成即结束本轮，不自动审查、不自动提交，修改保留在工作区；开启且本轮有受控代码修改时，使用固定 Review 提示词审查，后续问题选择、修复复审及本地提交沿用现有流程。纯问答无代码修改时，即使开启也跳过审查和提交。跳过审查的轮次显示“已完成（未审查）”，可以继续对话和上传图片。首次需求实施仍自动 Review 并按现有规则本地提交。

每条后续消息形成独立交付轮次，原消息、图片、计划、审查及提交记录保留，并记录本轮 Review 开关。开关随当前文字草稿按浏览器标签页保存，发送成功后下一条重置为关闭，发送失败保留选择。已发送轮次的开关随会话持久化，暂停、恢复及重新计划不改变。历史运行中轮次缺少开关字段时维持原有流程。图片在发送前可移除，发送后在对应消息中只读展示；上传失败须明确重试或移除后再发送。待发送的已上传图片和正式消息可在刷新或重启后恢复。历史 Review 只读，本轮只合并本轮审查问题，不把上一轮已接受问题自动列为待修复。

发送后，页面在首段回复前显示等待提示，开始输出后显示实时文字。原线程历史较长时，模型首段输出可能较慢。控制器按原线程记录已发送的上下文字段和图片内容，仅补发变化字段和新图片；重连继续去重，新线程或图片内容变化时重新发送。模型指令在线程初始化或恢复时提供，不在每轮重复加载。`task_context` 默认返回当前授权和资料版本，首次分析或版本变化时显式设置 `include_materials=true`，归一化正文保留版本与归属，原始接口记录只在控制器保存。当前文件与基线均默认读取 200 行、最多 500 行，按 `next_line` 续读；`read_files` 可一次读取最多 10 个片段、合计 2000 行，并通过每项 `baseline=true` 对照基线。精确路径搜索直接读取目标，glob 按固定目录前缀裁剪扫描范围。审查提交工具遇到文件内容变化或范围无效时返回具体原因，需要用户确认的内容通过问题卡片等待明确答复；工作流已登记的 MCP 工具调用直接允许；阶段授权、计划版本、文件范围和共享文件版本校验统一在工具入口执行，校验失败返回具体原因，不再被转换成“user rejected MCP tool call”。

后续对话沿用当前会话绑定的前后端仓库与目标分支，重新按现有目录分配规则确定工作区，并以目标分支当前 HEAD 建立本轮基线。目录切换冲突、原分支被占用或 Git 钩子阻止操作时明确停止，人工处理后点击“从暂停点继续”，不会重复创建消息。已有本机改动及上轮未提交代码仍保留且不自动修改或纳入本轮提交；需要修改同一文件时等待明确指示。本轮首次修改不占用 Review 后的问题修复次数，复审次数沿用配置；后续提交使用 `fix(...)`，部分成功时仅继续未完成仓库。完成后可再次发送消息，不 push、不修改禅道状态。

用户明确要求修复上轮代码时，`replace_text` 可修改本会话历史交付中可追溯、内容未被外部改变的任务文件，不再将其误判为无关本机文件而拒绝。精确替换仍须匹配唯一一处，连续替换记录按本轮授权独立保存；控制器在回合结束时把实际替换文件纳入本轮检查与审查范围。其他本机保留文件继续排除；混入外部修改时返回具体原因，不自动覆盖。Review 开关、修复轮次和提交规则沿用原设置。

在对话中明确要求“重新 Review 并提交”“提交上轮修改”或“回退后重新提交”时，模型通过受控工具登记请求，由控制器重新审查并在无遗留问题后本地提交，此请求不受“修改后自动 Review”开关限制。需要纳入上轮未提交代码或回退后保留的任务代码时，控制器按历史任务记录核对文件，本机其他保留改动继续排除；模型核对当前差异属于本次任务范围后直接登记，不因历史快照不同重复要求确认提交。来源不明、包含无关改动或范围不清时先澄清。请求登记后文件再次变化会停止。可直接指定提交标题或摘要；现有 Review 回合按各仓库实际差异生成 `type(实际模块): 中文摘要`，人工摘要逐字保留并补全格式，已符合规范的标题保持原样。完整标题最多 72 个字符，工作项编号由控制器放在正文末尾。缺少有效标题时停止并明确重新 Review，不拼接原标题或自动重试。请求登记不代表提交完成，有问题及提交失败仍按原流程等待人工处理。

本地接口 `/api/actions` 新增 `followup`，以 `data.text`、`data.image_ids` 和必填布尔值 `data.review_enabled` 提交本轮消息，沿用 `session_id`、`revision` 和 `request_id`。图片接口以 `purpose=followup` 管理后续对话图片，省略用途仍按原需求补充图片处理。删除会话纳入历次自建工作区，继续检查其他会话占用与未提交文件，保留复用目录。

### 所属项目与分支识别

工作项列表和资料快照保留所属项目编号、名称及多个项目候选。任务详情仅返回编号时，通过项目详情接口补齐名称。归属缺失或多个项目时，先明确本次所属项目，不用产品或迭代名称代替。前后端分支分别判断，名称可以不同。

AI 根据项目名称、工作项及补充说明，从真实分支中分页筛选候选，再由控制器读取候选最近十条提交复核。允许项目简称、别称及期次修饰，不要求完全同名，不编造分支名称。先判断项目归属及长期维护性质，优先项目 `dev/develop` 开发主线，再比较同等匹配候选活跃度；带日期、人员、备份或功能主题的分支不能只因更新晚就优先。证据不足以结构化结果返回问题，等待人工选择。该线程不提供业务文件工具。

分支识别先由 AI 从项目名称、正文及人工补充提取最多五个明确地名或项目主体关键词，如“绍兴、资阳、传化”，不使用“档案馆、售后、dev”等通用词。“绍兴市”归一为“绍兴”，匹配“绍兴市档案馆/develop”“绍兴馆藏二期/develop”等现有命名。关键词必须在资料中出现，不猜测拼音、缩写或分支名。

本地先扫描引用名称，筛选名称包含关键词的分支后，读取命中引用的元数据和最近十条本地可用提交。AI 结合地名、项目范围、分支性质和提交时间，直接选一条最新的开发主线；功能、专题、个人临时修复和备份分支均排除，不再分页初筛或限制候选数量。AI 返回的依据说明项目匹配、开发主线性质及最新提交时间。远程新分支没有本地历史时标明未验证，只对选中的远程分支按原规则定向拉取，再复核真实提交，不批量拉取命中的所有远程分支。

需求正文首次发送到分析线程，后续按版本指纹复用；正文变更或更换线程后重新发送。各 clone 及本地、远程引用的提交信息分别保留，不向 AI 发送无关分支。无法提取关键词、无法确定开发主线或刷新一次后仍无匹配时等待人工选择，不扩大为全库分析。旧会话停在分页初筛时，恢复后会丢弃旧分页进度，直接重新判断目标开发主线。每轮输入超过 Codex 的 1,048,576 字符上限时明确停止，不截断证据或自动重试。

没有合适分支，或候选仅存在于缓存远程引用时，先用 `git ls-remote --heads` 对配置的远程刷新一次清单，再对候选执行带明确 refspec 的 `git fetch --no-tags`，读取实际提交历史复核。鉴权或网络失败即停止；恢复操作不会切换凭据、远程或模型。已被远程删除的缓存引用不会当作有效远程分支使用。

AI 无法确定时，页面展示依据、候选和疑问，必须明确选择后才能继续。“保存为项目常用分支并继续”按禅道站点、项目编号和仓库角色保存人工选择；AI 自动结果只用于当前会话。后续优先复用常用分支，失效时要求重新选择。在创建工作区之前，可通过“更换项目常用分支”主动调整。

每个仓库可在配置中增加 `candidate_paths`，与 `path` 合并并按目录去重；省略时仅检测 `path`。例如前端配置 `"path": "D:/wkproj/ais-web", "candidate_paths": ["D:/wkproj/ais-web-2"]`，后端对应 `ais-server` 和 `ais-server-2`。候选目录可以是独立 clone，真实分支及提交元数据逐目录记录，目标分支确定后才比较匹配目录的 HEAD 提交者时间。

首次准备优先使用已检出目标分支的目录；无匹配时按配置顺序检查空闲目录并切换，全部不可用时创建独立工作区。其他未完成会话占用的目录不切换，相同目标分支按现有规则共享。干净目录直接可用；有修改时，AI 逐文件核对已暂存、未暂存、未跟踪差异，只有全部确认为非功能调整才可携带，无法判断则跳过。日志、依赖和字体也按内容及用途判断，不按文件名放行。判定记录保存差异指纹，操作前再次核对，变化后重新分析。

自动智能切换通过 Git stash 保留文件及暂存状态，本机改动继续排除于任务提交。携带改动冲突时恢复原分支、文件和暂存状态并停止，等待人工处理；无法完整回退时保留 stash 及进度，不继续分配。目录检测与人工选择仍使用 `/api/actions` 的 `detect_repositories`、`choose_repositories`，保留会话版本和重复请求约束；检测结果增加分配动作，AI 判定记录包含逐文件结论及依据。

旧暂停或待答会话的记录分支已与目录实际分支不同，不再阻止复用已检出目标分支的目录，也不阻止目录的空闲判定与切换；复用时保留已有改动，切换前当前文件仍须确认没有功能修改。实际分支匹配的有效占用、执行中会话以及释放或交接保留继续阻止切换；执行中会话的分支冲突及交接、释放仍阻止共享。删除仍核对完整归属，旧会话记录不自动改写。

`workspace_root` 默认为 `D:/wkproj/worktrees`，新建工作区按会话及仓库、交付轮次分目录，首次准备、续聊重新分配和重试共用，不允许创建到 C 盘。现有 D 盘历史工作区保留原位置，归属检查和删除兼容新旧布局；配置的日常开发目录仍可直接复用。

已有会话在“变更目录与审查基线”弹窗检测候选目录，仍须预览并明确确认才更新绑定及基线。未完成会话恢复和续聊沿用绑定目录；已完成会话续聊重新分配时优先复用目标分支目录，必要时切换空闲目录或在配置根目录创建工作区。同分支共享、占用、交接和钩子限制保留。尚未准备工作区的会话重新识别时清除旧 AI 判断与目录检测，保留人工选择，不自动改变已绑定目录。

首次或续聊准备工作区失败时，在“准备工作区失败”或尚未准备完成的“已停止／已暂停”会话中，可点击对应仓库的“预览复用已有工作区”。仅识别 Git 已登记、检出原目标分支且位于会话管理目录之外的外部工作区，不接受任意目录或接管其他未完成会话。预览展示目录、分支、当前 HEAD、最近提交、占用情况和本机保留文件；刷新或重启后仍须明确点击“确认复用并继续”，也可取消或重新预览。预览后登记、分支、HEAD、文件或占用关系变化时须重新预览；锁定、登记失效及受限 Git 钩子仍阻止复用。

确认以该目录当前 HEAD 建立本轮初始基线，该提交及之前的代码不计入本轮差异，已有未提交修改（含暂存和未跟踪文件）按本机保留内容排除。仅登记当前会话的绑定及确认历史，不切换分支、不搬迁文件、不修改全局配置，然后按原首次准备或续聊入口继续，保留原线程、消息、附件及轮次。其他仓库后续准备失败不撤销已确认的绑定；删除会话保留外部目录。新会话没有匹配目录时等待人工处理；历史工作区保留原有分配规则，同一分支已在其他目录检出时不强制重复检出。

本地接口 `/api/actions` 支持 `preview_workspace_reuse`（`data.repository` 为尚未准备成功的仓库名称）、`confirm_workspace_reuse`（`data.token` 为预览凭证）及 `cancel_workspace_reuse`，沿用会话、版本和请求编号校验。预览保存在会话的 `workspace_reuse_request`，确认后写入 `workspace_reuses` 历史并登记非自建工作区；历史会话无需迁移即可预览。

复用目录开始时已有的已暂存、未暂存和未跟踪改动按文件登记为本机保留内容，不进入任务差异、审查清单和提交；已有暂存状态也会保留。文件工具拒绝自动修改这些文件，需要改动时须先取得用户明确指示。任务提交只包含本次任务的文件。分支切换仍受 Git 自身的覆盖检查约束，冲突即停止，不自动切换其他方案。

### 任务关联需求资料

普通任务（`fromBug` 为 0）的关联需求固定使用任务详情接口返回的 `storySpec`、`storyVerify`、`storyFiles`，保留关联编号、标题和 `storyVersion`，不再单独请求需求详情。这样可兼容当前禅道中关联需求实际类型为 `requirement`、按研发需求接口读取却报“对象不存在”的情况。

普通任务的页面会标注“来自任务详情的关联需求资料”和关联版本；内容对应任务所关联的版本，可能不是需求的最新版本。该关联资料不会作为独立用户需求加入待办列表。正文图片、附件及飞书链接仍按现有规则处理。

来源 Bug 的任务（`fromBug` 非 0）由禅道返回来源 Bug 描述，不包含上述关联需求正文字段。因此这类任务保留原有读取路径：有需求关联时请求需求详情，再读取来源 Bug 详情，正文、验收标准、图片和附件一并采集。不将需求接口返回的资料标为任务内嵌资料或任务所关联版本；关联请求失败时明确停止，不自动重试或尝试其他需求类型。

关联正文为空而任务描述有效时，可依据任务内容进入计划，不会将任务描述复制成需求正文。任务和关联资料均无有效正文时仍要求补充；描述冲突或验收标准不清时在计划阶段询问。附件缺失继续提示人工补充，任务自身读取失败或权限失效仍停止，不自动重试。独立需求、Bug 及任务来源 Bug 的读取规则不变。

## 刷新与历史

- 实施计划和 Codex 消息支持 Markdown 标题、列表、任务列表、表格、引用、链接和代码块，兼容 `<proposed_plan>` 包裹；渲染使用本地资源并清理 HTML，原始计划及确认版本不变。Review 的修复选择、不修复记录、复审、追加轮次及本地提交记录统一在“计划与会话”中查看。
- 实施计划卡片支持“查看详情”，在更大的弹窗中阅读完整计划和版本，长内容可滚动，窄屏自动适配；支持关闭按钮和 Esc 退出。详情只用于查看，不触发计划确认；切换会话或页面时关闭详情，续聊中的原需求实施计划同样支持查看。

- 会话卡片顶部显示独立标题。新建任务、Bug、需求会话在首次计划分析读取完整资料后，由当前模型结合标题、描述、关联资料及补充说明生成简短中文名称，建议 6～12 字、总长不超过 20 个字符；多任务会话概括首个任务并追加“等 N 项”。生成前显示“待命名会话”，未生成成功不阻塞计划、不额外启动命名回合；中断后随后续计划回合继续生成。历史会话保留原名。点击“改名”可自定义，人工命名始终优先；刷新、重启或续聊后名称保留。下方始终显示完整工作项信息，搜索同时匹配会话标题与工作项信息。
- 升级后新建的工作流会话，在 Codex 中显示为“工作流会话 · 平台会话名称”。线程创建、平台自动命名和人工改名后异步同步，分支识别及正式执行线程使用同一名称；断开连接时留待下次连接处理，不额外启动模型回合。同步失败会提示并在会话消息中保留原因，本会话停止名称同步，不自动重试或切换接口。升级前的历史会话保留 Codex 原名。

- 工作项、计划与会话页面左侧按所属禅道项目折叠展示会话，项目标题显示编号和筛选后的会话数量；项目内按用户或 AI 最近对话时间倒序排列，项目分区按其最新会话时间排序。“无项目对话”固定显示在末尾。支持新建、会话或项目名称与编号搜索、状态筛选、切换与删除；当前浏览器按应用地址持久记住各分区（含“无项目对话”）的折叠状态，刷新、重新打开浏览器或下次登录后恢复。搜索时临时展开命中分区，清空搜索后恢复已保存状态。
- 会话左下角显示最近对话时间，查看、改名、状态保存和服务重启不改变此时间。没有对话时显示“尚无对话”并排在分区末尾。用户最后发言距今超过 120 小时的会话置灰并标注“超过5天未对话”，仍可查看和操作；AI 回复更新排序但不解除置灰，用户再次发言后恢复。没有用户发言的会话不置灰；页面每分钟及重新切回前台时更新判断。
- “添加项目分区”从当前账号可见的禅道项目中下拉选择，支持按名称或编号搜索；仅在本地添加，不在禅道创建项目。重复项目合并，手动添加的空分区按站点保存，刷新或重启后保留。项目归属确认也使用可搜索下拉框，分支下拉框支持按显示名称搜索。
- 查看资料时可在“项目信息”选择本次执行项目，重新读取资料保留明确选择；开始计划后使用该项目识别分支并锁定归属，计划失败或暂停也不解锁。查看资料仍不会创建正式会话。
- 旧的未启动会话可拖至项目标题或内容区，也可通过“移动”菜单更换项目；移入“无项目对话”后开始计划时须明确确认项目。移动修改本地会话执行项目及分析快照，保留原始工作项资料，不修改禅道中的工作项归属。已启动计划、已有分支识别记录、线程或工作区，以及正在执行或清理的会话均禁止移动。
- 支持多个会话同时运行；每个会话有独立的执行队列、Codex 连接、输出与操作版本。切换只改变查看对象，不会暂停或重启其他会话，后台问题会标记在对应会话上。
- 同仓库、同分支的会话共享已有目录，不再因未完成会话占用而阻止开发。不同分支沿用空闲目录切换或新建工作区；切换、交接、释放、删除仍检查其他使用者。文件写入和 Git 修改操作短时串行，模型分析不独占目录。工作区信息展示共同使用的会话；删除自建目录所属会话时，若仍有其他会话引用该目录则停止，不搬迁代码。
- 点击“新建会话”后仅进入工作项查看页面；勾选后自动读取资料，任务可多选联合开发。读取成功或失败均不进入会话列表，失败时可明确点击“重新读取资料”。仅点击“开始需求分析与计划”且服务端接受后才创建会话，重复点击不会重复创建；开始计划后工作项固定。
- 浏览器刷新后重新加载当前工作项、阶段、计划、待回答问题、Review 和提交记录。当前选择按浏览器标签页保存，不同标签页可分别查看不同会话。
- 正式会话的问题答案、人工分支选择和 Review 选择按会话分别保存为当前标签页草稿；开始计划前的工作项选择、补充说明和图片只保留在当前页面。密码不进入草稿。
- 实时输出通过 SSE 推送，连接中断后恢复事件流；服务重启后需刷新页面重新连接。
- 服务重启后所有中断执行的正式会话显示为已暂停，须人工继续；临时查看不会恢复，需重新选择工作项读取。停止服务会保存正式会话并清理临时资料。已有历史记录保持原样，不迁移或删除以前仅查看或读取失败的会话。
- 删除会话时一并删除本地资料、附件和本会话新建的独立工作区，保留复用目录、Git 分支及提交。执行中的会话须先暂停并等待结束；待删除工作区存在未提交、未跟踪文件或被其他未完成会话使用时会阻止删除。复用目录中的本机保留改动不影响仅删除会话记录。
- 工作区全部预检通过后逐个移除，不使用强制删除。中途失败保留会话记录及清理进度，再次删除只处理剩余工作区；清理过部分工作区的会话只能继续删除。
- 原桌面客户端的 JSON 会话、附件及 Windows 加密凭据继续使用，不要求重新配置账号。

## 配置与凭据

### 原生工具与 MCP 继承

普通业务会话自动继承同一 Codex 主机上已启用的原生工具、全局 MCP、Apps 和插件配置，联网搜索也沿用本机设置；后续新增的全局工具由 Codex 发现，不逐个接入工作流。工作流 MCP 的工具清单直接从工具注册表生成。分支识别线程仍只分析输入，不开放工具。桌面客户端动态注入并由客户端执行的专属工具，不会自动复制给独立 App Server 进程，不能承诺与桌面会话的工具清单完全相同。

单个工作流通常只使用一个正式 Codex 线程，计划、实施、Review、修复、编译分析、续聊及暂停恢复均复用；只有需要 AI 判断分支时增加一个不开放工具的识别线程。已有有效项目常用分支或人工指定分支时跳过 AI 识别；重复发起识别复用原识别线程。两类线程保留独立的工具与规则配置，改名不增加模型回合，重连和切换模型不新建线程；原线程恢复失败时停止，不另建替代线程。历史中已经创建的线程保留。

线程通用规则通过创建、恢复时的 `developerInstructions` 提供，回合保留阶段职责、需求范围、资料读取提醒、最新授权和审查约束。需求上下文只发送变化字段，图片按内容去重；历史页面说明规则仅在线程首次接收或规则内容变更时附加，记录随会话保存，发送失败不标记为已发送。提问等待与变化字段约定不再在回合包装中重复。精简的是重复输入，不保证模型计费或处理耗时按相同比例下降。

原生 Shell 仅授权只读检索，保留只读沙箱和原生写入、提权拦截；业务文件仍通过工作流工具修改、校验版本并记录差异。编译、构建、运行验证、依赖安装、Git 修改和提交继续遵守既有控制器边界。非工作流 MCP 的调用授权请求复用现有问题卡片，必须明确选择“允许本次”或“拒绝本次”；不自动放行，也不再统一当作用户拒绝。未支持的 MCP 自定义表单及 URL 授权流程仍不自动转换或执行。工具发现不代表获得外部写入或发送授权，沿用用户任务范围和原生工具策略。

### 只读 Git 查询

模型可在当前会话绑定的仓库中使用 `git_log` 查看提交历史（可按路径筛选）、`git_files` 浏览指定版本的文件、`git_file` 读取指定版本文件、`git_diff` 比较两个版本。`ref` 支持本地分支、远程跟踪分支、标签和提交号；差异的起点用 `base_ref`。这些工具读取本地已有对象，不切换分支、不拉取、不修改工作树、暂存区或会话基线；引用不存在时明确停止。

历史默认每页 20 条、最多 100 条；文件清单默认 200 项、最多 2000 项，均沿 `next_offset` 续读。文件和差异默认 200 行、最多 500 行，沿 `next_line` 续读，单次内容上限 4 MiB。返回的提交号可用于固定后续查询，避免分支移动导致分页内容变化。依赖、Git 和输出目录继续排除。版本文件不登记当前文件的读取记录，也不提供写入用的 `version`；修改前仍需读取当前文件。新增工具在服务更新并重新建立 Codex 连接后可用。

### Review 前的可选后端编译检查

在“工作流设置”勾选“Review 前自动检查后端编译”可设置新会话默认值；开始会话前可单独调整，开始后固定并沿用到后续对话。配置字段仍为 `compile_check.enabled`，初始为 `false`，已有开关值保留。开启后，每轮实施或修复完成，只检查有任务改动的后端，再按原 Review 设置继续；仅有前端改动时直接进入原有 Review 流程。后续对话关闭 Review 时，后端编译检查完成后仍只保留修改，不自动审查或提交。

后端复用 Maven 本地仓库，先离线执行 `compile`，按改动所属模块及所需模块检查。例如修改档案服务即检查档案服务及其所需模块；工程级配置变化检查整个工程。不执行测试、打包、`install` 或发布。工具或配置不兼容时停止，不自动更换版本或切换依赖源。前端不再调用 pnpm、不安装依赖，也不受前端锁文件与工具版本影响；前端代码仍完整参与 Review。已有相关 Git 钩子时仍停止，不禁用或绕过。

缓存不足时，必须明确点击“补齐依赖并重新检查（允许下载）”“跳过该仓库本轮检查”或“暂停”，无默认答案。缺少 Maven 插件同样进入依赖补齐选择。下载和跳过只对当前仓库、本轮代码与依赖配置有效，后续新检查不会继承授权；下载失败后停止。页面展示状态、脱敏失败原因及必要代码诊断，不展示原始编译日志或堆栈。旧记录没有保存具体原因时明确提示重新检查，不猜测历史原因。

检查子进程统一以 UTF-8 输出诊断，按完整行收集后严格解码，不修改业务源码编码；不兼容的输出会明确停止解析，不替换成乱码。页面单独展示“报错服务”（优先使用 Maven 失败项目，否则根据诊断文件所属模块定位）与“检查范围”，不会将所有参与检查的模块都标记为失败服务。无法定位服务时明确说明。旧记录含无法还原的乱码时，保留可读失败信息和可识别的服务名，并提示重新检查。

失败仓库可点击“分析失败原因”，在原会话中只读分析诊断、当前代码及基线，返回缺少内容和建议处理办法；分析不修改文件、不下载、不自动进入 Review 或提交。已明确诊断的本轮代码错误提供“修复代码并重新检查”，达到上限时仍须人工追加一轮；环境、网络及来源不明的问题不能通过修复按钮扩大修改权限。

诊断明确位于本轮修改代码时自动修复并重查；原有、环境、网络及原因不明的问题暂停。检查未通过时可点击“授权 AI 修复并重新检查”，授权 AI 先只读核实诊断和当前源码，再修复已经确认的代码错误（含原有代码问题），只开放已核实文件；本机保留文件仍不自动修改。缺少结构化诊断时仍可结合已有分析核实，证据不足则停止；依赖下载、环境变更不在代码修复授权内。自动修复沿用会话修复上限，每次进入 Review 前独立计数，不占 Review 修复次数，超限可人工追加一轮。通过或被明确跳过后才进入 Review，检查结果随 Review 上下文提供。暂停或停止服务会终止检查进程，重启后须人工恢复；普通恢复不会代替下载、跳过等选择。

提供给模型的检查上下文仅包含当前交付的状态、模块、必要诊断及受控修复范围，不传文件哈希、人工授权明细或时间戳。Review 与修复提示词不再重复附带检查记录；完整记录仍保存在本机会话中。旧的前端检查历史保留，尚在等待的前端检查可点击“前端检查已取消，继续后端流程”继续，不执行前端命令。

本地接口 `/api/actions` 增加 `compile_decision`，`data` 包含 `batch_id`、`repository`、`decision`；操作为 `download`、`retry`、`skip`、`pause`、`add_round`、`fix`、`analyze`，沿用会话版本和请求去重。`plan` 与设置保存使用 `compile_check_enabled` 布尔值。

`settings.json` 是唯一的本地运行配置文件，保存禅道地址、账号、仓库路径、项目常用分支、Codex 命令、默认模型、推理强度和修复轮次，已加入 Git 忽略规则。公开仓库只维护脱敏模板 `settings.example.json`。

网页“工作流设置”支持从本机 Codex 的可用模型中选择默认模型与推理强度。模型选择“沿用本机 Codex”时，`codex.model` 保持为空；`codex.reasoning_effort` 保存明确的强度。模型和强度以本机返回的列表为准，点击“刷新模型列表”可重新读取；无法读取或组合无效时不会启动会话或自动更换模型。

在工作项资料下方、点击“开始需求分析与计划”前，可以单独调整本次会话的模型与推理强度，不改变全局默认值。开始时将实际模型及强度保存到会话，之后识别分支、计划、实施、Review 和暂停恢复均使用该配置；刷新页面或重启服务后仍保持。已启动的会话可点击顶部“更改模型”，在空闲时选择并保存新的模型与推理强度；执行中需先暂停并等待当前操作结束。保存后从下一次模型调用生效，沿用原 Codex 线程、计划、待答问题和工作区，不自动恢复执行，也不改变其他会话或全局默认值。切换模型后若原强度不受支持，需重新选择；列表读取失败、配置无效或页面版本过期时不保存。旧会话未保存模型配置时，继续前需先在“计划与会话”页面选择并保存一次。

`repositories` 必须恰好登记一个 `role: "frontend"` 和一个 `role: "backend"`，每项明确填写 `name`、`path`、`remote`。`project_branches` 初始为 `{}`，页面确认后按“站点 → 项目编号 → branches → frontend/backend”保存常用分支；不会从项目名称猜测仓库角色。升级旧配置时，为已有两端仓库补齐角色与远程字段，保留原账号、路径及其他设置。

`prompts/review.md` 保存用户提供的固定 Review 原文。流程开始后锁定配置；流程内若提示词被外部改写，会明确停止。

密码仅通过 Windows 当前用户 DPAPI 加密保存在 `.local/zentao-password.bin`。页面不回显密码，服务不向前端返回禅道 Token。`.local/` 和 `work/` 已加入忽略列表，包含业务资料或检查中间文件，不应上传或提交。

## 后续开发与推送

直接在当前目录开发、提交和推送，无需同步到其他副本。本地 `settings.json`、加密凭据及会话资料继续使用，Git 更新不覆盖它们。修改配置结构时同步更新 `settings.example.json`，使用者再按模板手动调整本地配置。

```powershell
git diff
git add README.md
git commit -m "docs(workflow): 完善工作流使用说明"
git push origin main
```

上面的 `git add` 路径按本次实际修改文件替换。提交采用 `type(scope): 中文说明`，详细约定见 [贡献与提交规范](CONTRIBUTING.md)。应用自身只进行本地提交；向 GitHub 推送由使用者明确操作。

## 页面与本地接口

前端使用 AIS 项目已有的 React、Ant Design 和 dayjs 发布资源，采用相同的主题色、按钮、表格、表单及弹窗组件体系。资源已复制到 `web/dist/vendor/`，版本记录和许可证一并保留，页面不访问外部 CDN，不需要构建。

本地 HTTP 服务提供工作流操作、分支读取、差异查看、受限附件访问及 SSE。`GET /api/session?id=...` 读取指定会话，差异接口使用 `session_id` 指定会话；`/api/actions` 按 `session_id` 分发操作，包含 `delete_session` 删除操作。会话 SSE 携带 `session_id`，完整状态还包含版本和事件游标。操作要求本机来源、会话 Cookie、独立操作凭据及明确请求标识；重复请求不会重复执行。计划确认、修复选择、提交和删除还检查页面所见的会话版本。

核心仍由 `workflow/engine.py`、`rpc.py`、`mcp_server.py`、`gitops.py` 等模块负责。原生只读沙箱与受控 MCP 文件工具继续使用；文件写入只在已确认的实施、修复阶段授权。

## 支持范围

- 禅道 API v1：账号密码登录、当前用户、分页待办、详情、关联需求 / 来源 Bug、附件及正文图片。
- 禅道资料读取：UTF-8 文本及不含内嵌媒体的 DOCX、PPTX 提取文本；ZIP 展开成员并保留来源归属。PDF（含 ZIP 内的扫描件）通过 Poppler 的 `pdftoppm` 逐页生成图片，在页面中预览，并随计划回合交给 Codex 阅读。在 `settings.json` 中配置 `pdf.renderer`，推荐使用 `pdftoppm.exe` 的完整路径（例如 `D:/tools/poppler/Library/bin/pdftoppm.exe`），正常启动时无需依赖临时 PATH；命令名仅在启动环境的 PATH 中解析。配置的工具不可用时明确停止 PDF 读取，不自动查找其他路径或切换解析方案。电子表格、旧版 Office、加密文档及含内嵌媒体的 Office 文档仍提示人工补充。
- 飞书第一版不读取，只保留链接；必要规则由人工补充。
- 启动连接、重新连接和“全部”刷新都会读取五类待办。研发需求、任务和 Bug 通过 API v1 的 `user?fields=story,task,bug&type=assignedTo` 合并读取，完成后先显示。业务需求和用户需求共用可见产品分页结果，分别按产品和指派人查询，每批最多四个请求。本轮已取得的项目名称可供后续查询复用。
- 切换分类只筛选列表。手动点击“刷新列表”重新读取当前分类；“全部”下重新读取五类待办。页面显示读取进度和耗时，失败的分类保留上次成功结果，可手动刷新重试。服务重启后重新读取，更换连接配置时清空列表。过滤仍核对指派人、删除标记及排除状态。刷新状态的 `list_requests` 和 `elapsed_seconds` 用于定位请求次数和耗时。
- 项目列优先显示明确的项目名称。需求列表未提供项目关联时，读取该需求详情，并采用禅道明确返回的项目关联或关联执行中的所属项目编号；不把产品编号、执行编号或执行名称当作项目。项目名称优先在本轮工作项之间复用，缺失名称按不同项目编号分别查询一次。无明确关联或存在多个候选项目时显示“待确认项目”，继续由人工选择，不显示“项目 #0”，也不自动猜测所属项目。
- 模型对 Java 代码只做轻量静态检查；开启编译检查时仅由控制器执行受控例外。工作流自身的模拟验证不编译业务仓库、不下载业务依赖，业务功能仍需人工验收。

Codex 官方协议参考：[App Server](https://learn.chatgpt.com/docs/app-server)、[功能配置](https://learn.chatgpt.com/docs/config-file/config-basic)。

### 共享工作区与分片提交

每轮保存开始 HEAD、初始差异和暂存状态，MCP 写入独立记录修改前后内容。read_file/read_files 返回 version；write_file/replace_text/delete_file 的 expected_version 使用最近读取或保存返回的版本，新文件使用 missing。版本变化须重读后修改，防止覆盖读取后发生的新修改；读取最新版本后可按本轮授权接续修改其他会话涉及的代码，不再按跨会话归属拦截，也不要求额外交接确认。

Review 沿用现有流程，changes 返回差异片段编号和来源；fragment_ids 可按需读取片段正文。本轮实际修改的片段正常进入审查，同时保留涉及的来源会话记录。AI 按需求、修改记录及历史判断本轮范围，通过 commit_scope 逐仓库列出 include 和带原因的 exclude；人工、历史、其他会话及归属重叠的相关片段均可审查后纳入，无关改动仍须排除。本轮及明确请求审查的片段必须纳入或说明排除原因。只提交本对话需求涉及的改动，提交描述先用 git_log 读取目标分支近期记录，参考其模块命名和摘要表述，并遵守既有标题格式。控制器以临时索引提交确认片段，同文件无关修改、人工暂存与未暂存内容保持。共享目录的 HEAD 快进不会单独使会话失效，本轮片段及审查上下文变化仍要求重新 Review。

新 Review 使用协议 3；历史结果保持可读，旧审查不能作为共享分片提交授权。提交失败停止，由人工核对后继续，不自动重试或 push。运行中固定 Review 正文保持冻结，内置阶段指令统一精简，用户自定义正文不自动改写。
